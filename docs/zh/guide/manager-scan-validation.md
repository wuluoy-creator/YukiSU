# 管理器发现与扫描验证

内核根据包列表、APK 签名和受信管理器配置识别管理器。`packages.list` 的更新可能由安装、升级或其他包元数据变化引起，不能把每次事件都当作 APK 已变化。本文描述扫描缓存的当前行为及验证方法。

## 发现与调度

主要实现位于 [`kernel/manager/throne_tracker.c`](../../../kernel/manager/throne_tracker.c) 和 [`pkg_observer.c`](../../../kernel/manager/pkg_observer.c)。

- 初始化时安排延迟扫描；包观察器监听 `/data/system` 中 `packages.list` 的创建/移动相关事件。
- 观察回调只调度工作，不在 VFS 事件回调中执行 APK 扫描。扫描使用延迟工作，100 毫秒内的重复通知会合并。
- 常规扫描和显式重新扫描共用互斥锁；退出时移除观察，再停止排队、取消工作并释放缓存。
- 读取包列表发生短读、解析失败或分配失败时，放弃本次更新，避免根据不完整列表清理授权记录。

## 缓存命中条件

扫描仍会枚举上层安装目录，以发现新包及更新产生的新安装路径。进入已检查过的普通应用目录之前，只有以下信息均未变化才会跳过该目录：

| 比较项 | 用途 |
| --- | --- |
| 完整 APK 路径 | 识别安装目录变化 |
| 包对应的 appid | 识别应用身份变化 |
| 设备号与 inode | 识别同路径替换 |
| 文件大小、mtime、ctime | 识别文件或元数据变化 |

元数据获取失败时重新检查；签名读取前后元数据不同的 APK 不进入缓存。缓存仅减少重复目录遍历和签名读取，不授予管理器权限。

内置或动态受信的管理器不进入跳过缓存，需要认证时仍读取签名。识别到管理器不会清空其他普通应用的缓存。显式重新扫描会使缓存失效，以便动态可信签名变更后重新发现管理器。SuperKey 或动态管理器存在时，未变化的普通应用仍可利用缓存。

首次发现、新安装、APK 更新和显式重扫仍需要真实访问 APK。该机制没有针对应用名称的扫描例外，也不改变系统 inotify 的事件分发语义。

## 主机回归

在仓库根目录执行，需要 Python 3 和本机 Clang：

```sh
python3 scripts/ci/test_manager_scan.py --cc clang
```

测试提取生产 C 函数，以模拟 VFS、APK 签名读取和工作队列记录目录打开、签名检查、缓存及授权变化。覆盖重复扫描、路径/身份/元数据失效、动态信任、强制重扫、包列表读取失败以及退出后禁止重新排队。

自动化入口是 [`.github/workflows/manager-tests.yml`](../../../.github/workflows/manager-tests.yml)。它是内核管理器发现的主机回归工作流，不是 Android 管理器 UI 测试。脚本通过只能证明这些模拟分支符合断言，不能替代完整内核编译、真实文件系统通知或并发验证。

## 设备验证

使用测试设备上的匹配内核和管理器，分别覆盖内置签名管理器、动态受信管理器及 SuperKey 认证场景。记录源码提交、设备 KMI、实际加载的内核模块版本、APK 版本/签名与测试步骤。

1. 完成首次扫描后，触发多次不修改 APK 的包元数据更新，通过内核跟踪或测试构建中的计数确认普通应用目录不再重复打开。
2. 安装、更新、卸载并重装管理器，确认新路径能被发现，身份校验正常；同时覆盖随机安装目录和旧式直接包目录。
3. 使用测试 APK 覆盖同路径替换、文件内容修改、appid 变化及元数据读取失败，确认不会沿用旧缓存。
4. 修改动态可信签名并通过其正常配置流程触发重扫，确认新的信任状态生效，未受信 APK 不会仅凭缓存获得身份。
5. 同时触发包事件和显式重扫，检查死锁、链表损坏、引用泄漏及退出后重新排队等异常。

设备侧目录访问计数需要适当的跟踪或测试构建；仅看到管理器正常启动不足以证明缓存命中。报告中应分开记录功能结果、访问次数和内核日志，不把主机测试输出写成设备实测结果。
