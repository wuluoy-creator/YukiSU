# インストール・更新・復旧

[日本語ドキュメント](../README.md) · [詳細ガイド（英語）](../../guide/installation.md)

Manager APK のインストールだけでは root は有効になりません。対応する LKM を含む起動イメージを端末へ導入する必要があります。

## 前提条件

- ARM64、Android 12（API 31）以降、Linux 6.1 以降。
- 配布 LKM の KMI は `android14-6.1`、`android15-6.6`、`android16-6.12`、`android17-6.18`。Android のバージョンだけで選ばないでください。
- 通常は bootloader のアンロックと、起動パーティションを書き込み・復旧できる手段が必要です。
- 現在のファームウェアと一致する元のイメージを保存し、対象パーティションと A/B スロットを確認します。

```sh
adb shell uname -r
adb shell getprop ro.product.cpu.abi
adb shell getprop ro.build.version.sdk
adb shell getprop ro.boot.slot_suffix
```

上記は情報を読むだけのコマンドです。KMI 一覧はビルド対象であり、全端末の動作確認を意味しません。

## 通常の LKM インストール

1. [公開リリース](https://github.com/wuluoy-creator/ZySU/releases)から Manager APK を入手します。Actions の場合は最終成果物 `Manager-arm64-v8a` を使います。
2. ホームの状態表示からインストール画面を開き、端末の ramdisk 構成に合う元の `boot.img` または `init_boot.img` を選択します。
3. 内蔵 LKM、または対象カーネルに合う独自の `.ko` を使います。Manager が KMI を判定できない場合は手動選択が必要です。`init_boot` にはカーネルがないため、単独では KMI を取得できないことがあります。
4. 必要に応じて SuperKey などを設定し、パッチ処理を実行します。出力は端末の `Download` に保存されます。ファイルを選ぶ方式では自動フラッシュしません。
5. ログを確認し、端末に適した方法で出力イメージを対応するパーティションとスロットへ書き込み、再起動します。

通常の `boot-patch` は ramdisk に ksuinit と LKM を置き、起動初期にモジュールを読み込みます。HTTPS のファームウェアから起動イメージを抽出する入口もあります。実際に検出された形式とパーティションを確認してください。

root が既にある場合は直接インストールが表示され、A/B 端末では非アクティブスロットへのインストールも表示されます。後者では OTA が書き込んだ対象スロットのイメージと KMI を確認します。直接インストールはパーティションへ書き込みます。

## boot カーネルへの直接 LKM 注入

ローカルファイルと直接インストールでは、LKM を boot カーネルに埋め込む `boot-patch-v2` も選択できます。対象はカーネルを含む `boot.img` / `boot` のみで、`init_boot` や `vendor_boot` ではありません。

内蔵 LKM を使う場合は対象カーネルから KMI を検出し、通常方式の KMI 選択画面は使いません。形式・シンボル・ABI の検査があるため、すべての boot イメージが使えるとは限りません。これは `CONFIG_KSU=y` 対応ではありません。方式を切り替える際は同じスロットの古い ramdisk パッチも処理される場合があるため、ログと元のイメージを保存してください。

CLI の `boot-patch --out` は出力ディレクトリ、`boot-patch-v2 --output` は出力ファイルです。詳細は [CLI リファレンス](../../ksud-cli.md)を参照してください。

## 認証と起動確認

SuperKey 未設定時は Manager の署名設定に従って認証します。独自署名の APK では対応する LKM の信頼設定が必要です。[統合ガイド](how-to-integrate.md)を参照してください。

SuperKey 設定時はそのキーを使用します。「署名バイパス」は Manager を SuperKey のみで認証する設定で、Linux モジュール署名の無効化ではありません。「shell を許可」は Android shell UID の root 利用を許可し、adbd の有効化とは別です。

再起動後はカーネル認識、認証、UAPI、ksud のバージョンを確認し、必要なら ksud カードから内蔵プログラムを同期します。SUMHP は内蔵済みです。`auto` は適した OverlayFS、次に Magic Mount を選び、SUMH は明示的に選択します。OverlayFS / Magic Mount の変更は通常再起動が必要です。

## 更新と復旧

Manager は公開リリースを確認し、CI 更新チャンネルは提供しません。APK、ksud、カーネルモジュールは別々のため、APK 更新後も必要に応じて ksud の同期と起動イメージの再修正・再起動を行います。OTA 後は対象 KMI を再確認します。

ソースと今後のリリースは公開リポジトリ `wuluoy-creator/ZySU` に統合されています。旧 APK が `ZySU-Releases` を参照している場合、新しい更新先を組み込んだ APK を [ZySU Releases](https://github.com/wuluoy-creator/ZySU/releases) から一度手動で更新してください。上書き更新には同じ署名とより大きいバージョンコードが必要です。旧 APK を新しいリポジトリへコピーしても、内部の更新先は変わりません。旧リポジトリは履歴と移行案内のために残されます。

起動イメージの復元と完全アンインストールは別の操作です。復元には一致するバックアップや対応するパッチ除去処理を使います。完全アンインストールは userspace とモジュールを削除し、起動イメージの復元を試み、Manager を削除して約 5 秒後に再起動を要求します。現在の実装では復元が失敗しても後続処理が続くため、事前に元のイメージと外部の復旧手段を準備してください。APK の削除だけでは起動イメージは元に戻りません。

起動できない場合は、実際に変更したパーティションとスロットへ対応する元のイメージを復元します。モジュール障害ではセーフモードも利用できます。起動初期の hook が音量下の押下を少なくとも 3 回検出すると有効になり、userspace がモジュールを無効化します。検出タイミングに依存するため、イメージ復旧手段も必要です。

報告には端末・ファームウェア、KMI、各コンポーネントのバージョン、修正方式、スロットとログを添えてください。`ksud install` は userspace 導入用であり、起動イメージのインストールではありません。
